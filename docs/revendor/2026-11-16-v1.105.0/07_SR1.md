## The title-bar pass (rulings 3 and 4)

The windows this addon draws itself, with the controls on their title bands:

| Window | Control | Tooltip | Rest | Hover |
|---|---|---|---|---|
| Outfit window (`OutfitterRebornWindow`) | close (Core `MakeCloseButton`, owner `OutfitterReborn`) | "Close" (library `CloseTip`) | `close.rest` = `icon.tint` | `close.hot` |
| Outfit window | settings gear (`OutfitterRebornWindowSettings`) | "Open settings" (new key) | `icon.tint` | `text.link` (was `close.hot`) |
| Outfit bar header | close (Core) | "Close" | `close.rest` = `icon.tint` | `close.hot` |
| Outfit bar header | lock (the Master `locked` switch) | "Lock or unlock the outfit bar", and a second line naming the shared switch | `icon.tint` | `text.link` (was `close.hot`) |
| Outfit bar header | drag strip (the band, not a control) | "Outfit bar", "Drag to move. Right-click for bar settings." | none | none |
| Outfit, trigger, rebuild and progress dialogs (`NS.Dialogs.New`) | close (Core) | "Close" | `close.rest` = `icon.tint` | `close.hot` |

- **How.** A new `NS.TitleControl(btn, title, body)` in `core/CoreSetup.lua` paints the control's art
  through the skin facade's `Mark` (`icon.tint` at rest, `{ token = "text.link" }` under the pointer,
  recorded so that a skin switch repaints it, as Widgets' `HeaderButton` does). It hooks a tooltip,
  `NS.ShowTitleTip`: the game tooltip is owned at `ANCHOR_NONE`, the first line is in `gtip.title`
  and the optional body is in `gtip.body`, placed by `LibKa0s-Tooltip-1.0`'s `PlaceAttached`.
  Without that major, or with geometry it cannot read, the tooltip goes above the control by a
  relative point. The lock and the drag strip used to own the tooltip at `ANCHOR_TOP` in the
  tooltip's own color, and now use the same helper. The library's surfaces carry the closes
  unchanged. `W.HeaderButtons` was **not** adopted, because a helper over the existing controls is
  the smaller change. The header strip with a settings mark remains an adoption item under
  WowAddonStandards v2.113.0 (`03_ADOPTION_PLAN.md`).
- **State colors.** The lock changes its art (lock / unlock) and not its color, so it takes the mark
  colors.
- **Not title-bar controls, left as they are.** These are the list rows' gear menu (it keeps
  `close.rest` / `close.hot`, with its comments reworded), the sheet button on the character sheet
  (DEV-SKIN-SHEET-BUTTON), and Blizzard's `CharacterFrameCloseButton`.
- **Tests, red first.** `tests/test_titlebar.lua` is new. It has one case per window (the window,
  the bar, the four dialogs) and a case for the lock's body line and the drag strip. Every control's
  tooltip is owned by the control and is non-empty, in `gtip.title` under the kit's probe skin, so
  the check cannot pass on the tooltip's default gold, and it hides on leave. Rest and hover
  colors resolve to the tokens in every shipped skin, Ka0s Default first. Red before the change:
  the gear had no tooltip, the lock lit `close.hot`, and the lock and strip tips were in the default
  color. Two cases were re-pinned to ruling 4, which supersedes smoke round 2 design G5's "gear lit
  as the X is": `test_dock`'s gear case (hover `text.link`, the X keeps its own `close.hot`) and
  `test_skin`'s "header gear has no border" (the gear's art is an `S.Mark`, and the button gets no
  box). `tests/skin_surfaces.lua` now declares the gear's and the lock's art as the painted
  surface. `test_surface_parity` gains a Tooltip row, because `core/CoreSetup.lua` now leases
  `LibKa0s-Tooltip-1.0`. `.luacheckrc` lets `core/CoreSetup.lua` read `GameTooltip`.
- **Docs.** `docs/testing.md` and design §9.3 each get a `test_titlebar` row. `docs/smoke-tests.md`
  gets SK7. `docs/test-cases.md` was regenerated and the README Tests badge moved to 1598.
